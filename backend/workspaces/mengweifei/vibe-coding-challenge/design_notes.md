# 设计决策文档

## 1. 目标函数设计

### 目标的数学形式

MIP 模型最大化以下目标函数：

$$\text{Max} \sum_{i} \big( W_p \cdot \max(p_i, 0) + W_e \cdot e_i + W_t \cdot t_i \cdot e_i - W_m \cdot m_i \cdot e_i \big) \cdot x_i$$

其中:
- $p_i$ = `priority_score`（业务优先级分，负值置零）
- $e_i$ = 转化效率得分（CTR 30% + CVR_pay 30% + p_ab 40%）
- $t_i$ = 尾部商家指示（`ipv_roi_自然 < 1` → 1，否则 0）
- $m_i$ = 垄断商家指示（`ipv_roi_自然 > 20` → 1，否则 0）
- $x_i$ = 决策变量（分配给商品 i 的曝光量）

### 权重设定

| 权重 | 值 | 依据 |
|------|-----|------|
| $W_p$ (优先级) | 1.0 | 优先响应业务优先级打分，是最主要的排序信号 |
| $W_e$ (效率) | 0.5 | 效率应为重要次因子，但不压倒优先级，避免"马太效应" |
| $W_t$ (尾部公平) | 0.3 | 给尾部商家适度倾斜，权重不超过效率以免扭曲分配 |
| $W_m$ (反垄断) | 0.1 | 作为软约束惩罚项，避免头部 ROI 商家垄断但不过度压制高效商品 |

### 设计依据

按业务目标优先级排序：
1. **覆盖面** → 通过线性目标 + 最低分配阈值 `MIN_ALLOCATION=50` 促进"让更多商品获得配额"，目标函数本身是线性的，不会因单个商品得分极高就垄断全部预算
2. **效率导向** → 效率分高的商品在目标中更受青睐
3. **尾部公平** → $W_t$ 项为 ROI<1 的商家提供额外加权
4. **反垄断** → $W_m$ 项对 ROI>20 的商家施加轻度惩罚

## 2. 约束条件设计

### 约束清单及阈值依据

| 约束 | 值 | 依据 |
|------|-----|------|
| 总预算 | 200,000 | 以 `daily_incremental_imps_pool`（~91,905）为参考的约 2.2 倍，模拟平台可调用的曝光资源池 |
| 单商品上限 | 5,000 | 200 个商品均分预算为 1,000，5,000 给予 5x 弹性空间 |
| 单商家总配额 | 40,000 | 测试数据约 40 个商家，均分~5,000，取 40,000 ≈ 总预算 20% |
| 每商家商品数 | 30 | 200 商品 / 40 商家 = 平均 5 个/商家，取 30 给 6x 弹性但防止集中 |
| 每类目商品数 | 60 | 200 商品 / 20 类目 = 平均 10 个/类目，取 60 给足够空间但防止类目垄断 |
| 最低分配阈值 | 50 | 低于 50 曝光无实际意义，避免解出现大量 1-2 曝光的碎片化分配 |
| 破零最低约束 | ≥ 50% needed | 一旦决定扶持某商品，至少分配所需曝光的 50%，确保有意义 |

### 决策逻辑

阈值从测试数据分布推算（seed=42 时约 200 商品、40 商家、20 类目），确保约束既有限制作用又不至于过紧导致 infeasible。实际生产环境可从配置中心读取。

## 3. 异常处理策略

### 发现的数据异常

通过分析 `generate_test_data.py` 的埋入逻辑和 pipeline 日志，确认以下异常：

| 异常类型 | 发生率 | 处理方式 |
|----------|--------|----------|
| 字段缺失 (少 1 个字段) | ~0.5% | 自动填充 `None`，不影响其他记录解析 |
| 空字段 (字段值为 "") | ~0.3% | 安全类型转换，空字符串返回默认值 (0/0.0) |
| 空记录（chunk 末尾多余 `二` 分隔符） | ~2% | `parse_one_record` 检测空串后返回 `None`，不参与后续 |
| `imps_needed_xiuzheng=0` | ~3% | 破零时间计算中跳过除法 (`if imps_needed > 0`) |
| `real_imps=0` | ~2% | 破零时间公式中分母为 0 时直接返回 `base_time` |
| `base_time=0` | ~2% | 正常参与计算，结果为 0（表示已可立即破零） |
| `priority_score<0` | ~2% | 目标函数中 `max(score, 0)` 将负值置零 |
| `ipv_roi_自然=0` | ~1% | 不影响分配逻辑，仅影响 tail/monopoly 判定 |

### 处理原则

1. **不中断**：任何单条记录的异常不影响全量 pipeline
2. **可追溯**：异常记录到日志（INFO 级别做计数、DEBUG 级别做详情）
3. **安全默认值**：类型转换失败使用 0/0.0，确保 MIP 求解不崩溃
4. **统计输出**：pipeline 结束前输出异常汇总，供排查

## 4. 降级方案设计

### 设计思路

题目明确指出：ODPS 账号只有读权限，写入将抛出 `PermissionError`。系统设计为"先尝试写入，失败自动降级"。

### 降级流程

```
result_writer.py:
  1. 尝试 ODPS INSERT INTO (TableWriter)
     ├── 成功 → 结束，记录日志
     └── PermissionError / Exception
         └── 2. 降级到本地 fallback 目录
               ├── {ds}_quota_fallback.csv     ← 配额数据
               ├── {ds}_delivery_manifest.txt  ← 交付清单
               └── 3. 同时保存到 output/quota/ (标准输出路径)
```

### 交付清单内容

`{ds}_delivery_manifest.txt` 包含：
- 运行时间、分区日期、商品总数、扶持商品数
- 总分配配额、冷启成功数
- 交付文件路径
- 人工入库指引（设置环境变量 `MOCK_ODPS_WRITE_ENABLED=1` 或使用有写权限账号导入）
- 校验信息（MD5）

### 输出目录结构

```
output/
├── raw/          # 原始未解析数据 CSV
├── parsed/       # 解析后结构化数据 CSV
├── quota/        # 配额分配结果 CSV（始终生成）
└── fallback/     # 降级交付文件（写入失败时生成）
    ├── {ds}_quota_fallback.csv
    └── {ds}_delivery_manifest.txt
```

### 恢复机制

设置 `MOCK_ODPS_WRITE_ENABLED=1` 后重新运行 pipeline，即可成功写入 Mock ODPS；或使用 `--upload-only` 标志仅重新执行写入步骤。
